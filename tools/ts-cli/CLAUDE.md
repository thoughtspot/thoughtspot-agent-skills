# ts-cli — Conventions

Loaded when working in tools/ts-cli/. Covers architecture, known limitations,
and the extension pattern.

## Architecture

```
ts_cli/
  cli.py              — Typer app entry point; registers command groups
  client.py           — ThoughtSpotClient REST wrapper; handles token caching and auth. `request()` detects `files=` in kwargs and skips the default `Content-Type: application/json` header (`_auth_headers(multipart=...)`) so requests/urllib3 can set the multipart boundary themselves — required by `ts dbt`'s file-upload endpoints
  tml_lint.py         — Pre-import TML linter: lint_tml (the single-document model invariants + guid placement; the rule set is enumerated ONCE, in tml_lint.py's own docstrings, and gated by check_lint_invariant_list.py — do not restate it here or anywhere else). I15 is the misplaced-column-root-key gate (BL-232): `description` under `properties:` is silently ignored at import, so the TML validates clean and the value is lost — a denylist of root-only keys, not an allow-list of valid properties keys, because the linter gates imports. I13 is the dangling-`[formula_*]`-reference gate (BL-183, promoted from BL-178): a bracket id reference matching no `formulas[].id` is parsed as search tokens, so the formula fails to import (error_code 14516, live-verified 2026-07-30) — distinct from I9, which mandates the id form in the first place (pure functions, no I/O)
  tml_common.py       — platform-neutral TML YAML serialization (dump_tml_yaml) + import-response GUID parsing (extract_imported_guid) — relocated from tableau/ (BL-063 PR5); pure functions, Genie-vendorable
  formula_common.py   — platform-neutral formula/name transforms (resolve_name_collisions, add_formula_prefix, expr_is_aggregated, fix_double_aggregation, bare_column_name — the ONE definition of "this expression names exactly one column", shared by sv_translate's two classifier sites and sv_build_model's join index; a private copy in any of the three is the BL-217 duplication class, and the narrower one that existed there missed a qualified/quoted rename) — relocated from model_builder.py/tableau/naming.py (BL-063 PR5); pure functions, Genie-vendorable
  model_builder.py     — Tableau TML assembly + phased-import orchestration facade (pure functions, no I/O; TWB parsing lives in ts_cli/tableau/twb.py)
  tableau_translate.py — Tableau → ThoughtSpot formula translation entry point + orchestrator facade over ts_cli/tableau/ (pure functions, no I/O)
  snowflake_ops.py     — Semantic View diff (normalise_expr/exprs_differ/compute_change_set) + DDL lint (lint_sv_ddl) + SQL var substitution (parse_var_assignment/substitute_sql_vars, behind `ts snowflake exec` — BL-079) behind `ts snowflake` (pure functions, no I/O)
  sv_parse.py          — Semantic View DDL → structured dict (parse_sv_ddl) behind `ts snowflake parse-sv` — tables/relationships/dimensions/metrics/facts/custom_instructions/verified_queries/extension extraction (BL-100; pure functions, no I/O; reuses snowflake_ops clause-extraction helpers)
  sv_sql.py            — Snowflake SQL expression → ThoughtSpot formula text (translate_sql_expr); tokenizer + recursive descent + Snowflake function map (ts-snowflake-formula-translation.md as data) behind `ts snowflake translate-formulas` (BL-100; pure functions, no I/O)
  sv_translate.py      — Parsed SV → translated ThoughtSpot formulas (translate_sv_formulas); identifier resolution, column classification, window/LOD/semi-additive/USING handling behind `ts snowflake translate-formulas` (BL-100; pure functions, no I/O)
  sv_build_model.py    — Snowflake SV → ThoughtSpot Model TML assembly (build_model_tml_sv); inline Scenario B joins (equi/range/ASOF), SV synonym→display name, private columns, fact table detection, strip_formulas for two-pass import; imports formula_common shared transforms (BL-100 PR3; pure functions, no I/O)
  sv_introspect.py     — INFORMATION_SCHEMA → tables-spec + tables map (map_snowflake_type, build_tables_spec, build_tables_map, tables_map_from_parsed, detect_column_gaps); `tables_map_from_parsed` is the no-warehouse path behind `--tables auto` (BL-205) and routes through `build_tables_map` so the introspected and derived maps cannot drift on shape; Snowflake type → ThoughtSpot type mapping, cross-schema query building, column gap detection against existing TS tables (BL-100 PR4; pure functions, no I/O)
  tml_model_parse.py   — Dialect-agnostic ThoughtSpot Model TML parsing shared by sv_build_sv.py and dbt_build_export.py: column index (build_column_index), column_id resolution (resolve_column_id), dimension/metric/time_dimension classification (classify_column), join-graph walk (build_table_maps/collect_join_data — role-play alias vs. physical table identity), relationship naming (build_relationship_name), metric dependency ordering (order_metrics). Split out when ts-convert-to-dbt needed the identical parsing a second time (pure functions, no I/O)
  sv_build_sv.py       — ThoughtSpot Model TML → Snowflake Semantic View DDL (build_sv_ddl); Snowflake-specific: to_snake aliasing, aggregation SQL expressions, CA extension JSON, synonym/comment handling, DDL clause assembly. Dialect-agnostic parsing imported from tml_model_parse.py (BL-100 PR5; pure functions, no I/O)
  column_impact.py      — Pure helper functions for `ts columns impact`: `parse_dependents` (flatten v2 dependent_objects → dep list), `apply_subtype_labels` (LOGICAL_TABLE subtype → human label via subtype_map), `find_broken_formulas` (formulas whose expr references physical_col), `find_broken_rls` (RLS rules/paths referencing physical_col), `collect_affected_lb_ans_guids` (extract LB/Answer GUIDs from dep_lists), `build_impact_summary` (final JSON summary dict). All pure, no I/O — testable without a ThoughtSpot connection. I/O command layer is commands/columns.py (pure functions, no I/O)
  dbt_diff.py           — ts-convert-to-dbt Case B change-set computation behind `ts dbt-export diff`/`sync` (parse_schema_yaml_columns, compute_dbt_change_set): mirrors the `ts snowflake diff` "Mode C" pattern (snowflake_ops.py's compute_change_set) rather than a general YAML merge — diffs two flattened `{model: {col: {meta, relationship}}}` maps (the SAME parser applied to both the existing project's schema.yml text and a freshly-generated one, so both sides of a diff can't drift from each other's shape) and reports new/removed/modified rather than rewriting DDL. Scoped to the PRIMARY artifact only; models/semantic_models.yml is not diffed (open-items.md #4). Table-level new/removed detection is NOT this module's job — a table can have zero classified columns/joins and so no schema.yml entry at all, so table existence has to come from `.sql` file presence, an I/O concern the command layer (commands/dbt_export.py) owns (pure functions, no I/O)
  dbt/                  — dbt <-> ThoughtSpot engine package (split out of dbt_build_export.py under the file-size gate; same convention as databricks/, tableau/, report/)
    tags.py              — THE ts_* tag vocabulary, both directions: `_build_column_meta` (TML properties -> tags) and `tml_properties_from_ts_meta` (tags -> TML properties) are exact inverses, asserted property-for-property by TestFullPropertyRoundTrip. Covers all 13 documented column tags (docs.thoughtspot.com/cloud/26.9.0.cl/dbt-integration-metadata-tags, 2026-09-09) plus the ts-cli extensions ts_ai_context / ts_display_name / ts_formula and model-level ts_rls_rules. GENERATED_COLUMN_META_KEYS / GENERATED_MODEL_META_KEYS declare the generator's ownership boundary — `sync --update-metadata` clears only these, so a hand-authored tag outside the set survives (pure functions, no I/O)
    manifest.py          — compiled manifest.json (+ catalog.json) -> Model TML (build_model_tml_from_manifest), the Path Y reader behind `ts dbt build-model`: ts_join_* relationship tests, ts_* column meta, MetricFlow metrics, ts_rls_rules; untagged columns typed from catalog.json (pure functions, no I/O)
    model_from_schema_yml.py — raw schema.yml -> Model TML (build_model_tml_from_schema_yml) behind `ts dbt-export build-model`, the offline return leg: no dbt run needed, but no catalog.json types or MetricFlow either. extract_table_rls_from_schema_yml returns ts_rls_rules in Table TML shape for the caller to patch in (pure functions, no I/O)
    case_b_plan.py       — ts-convert-to-dbt Case B engine behind `ts dbt-export diff`/`sync`: project-state walk, existing-model name adoption, change-set assembly (build_case_b_report — shared by BOTH commands so they cannot disagree), plus the ts_* ownership merge (_merge_ts_meta) and the deletion-safety gate (_is_ts_only_column). Also `render_report_markdown` (`--format md`), the ONE renderer `diff`, `sync` and `sync --dry-run` all print through — so a reviewed plan and an applied plan cannot describe the change-set differently. Leads with the two `removed_*` lists because those are the only lines needing a human decision. Reads the filesystem; every write lives in commands/dbt_export.py
    cloud_api.py         — THE dbt Cloud Admin API layer (the package's one I/O module): profile+token resolution (resolve_dbt_profile — slugifies the profile name and prefers the profile's own recorded `token_env`/`keychain_service`, which the three hand-rolled copies did not, so a profile named "My Project" silently found no credential), latest_successful_run (status=10 only), and fetch_artifact with a disk cache at `<tmp>/ts_dbt_artifact_{slug}_{run_id}_{name}`, mode 0600. Keyed on RUN ID, not a TTL: a finished run's artifacts are immutable, so a hit cannot be stale and a new job invalidates by construction. This is where a round trip's 3-5 manifest downloads became 1. The token lives in memory only — `DbtCloudCtx.token` is `repr=False` and never reaches the cache path, the cache contents, a log line or an error message
    artifacts.py         — the dbt Core (ZIP_FILE) side, filesystem only: `resolve_artifact_zip` is what every `--file` flag now accepts — a ready-made `.zip` passes through, while a `target/` dir (or project root, or either artifact) is located by `find_artifacts` and packed by `pack_artifacts`. Removes "ability to zip manifest.json + catalog.json together" from the skill's list of USER prerequisites; it is a two-file operation over paths dbt already fixes. A missing `catalog.json` is REFUSED naming `dbt docs generate` rather than uploaded, because ThoughtSpot types Table columns from it and a manifest-only archive imports successfully with no column types — a silent degradation, not an error. Archive entries are flat at the root (the literal reading of "a ZIP containing manifest.json and catalog.json"; not verified against a live ZIP_FILE connection — coverage-matrix L6), and the default destination is keyed on the source dir so `create`/`generate-tml`/`generate-sync-tml` rewrite one temp file rather than leaving three copies of a manifest that can run to hundreds of MB. Also holds `load_local_manifest`, the read half behind `--manifest`
    node_paths.py        — the ONE answer to "which model directory does this manifest node belong to", shared by manifest.py and inspect.py so they cannot drift. A model is placed by its own `.sql` dirname (exact, so `models/staging` never absorbs `models/staging_archive`); a TEST is placed by the model its `attached_node` names, NOT by the schema.yml that declares it — those are different directories whenever schema.yml sits above the models, which is exactly the layout `ts dbt-export build` generates. Matching tests by the declaring file made both readers report zero joins there, and zero joins silently downgrades a Path-Y project to Path N (ts-convert-from-dbt open-items #18, found live 2026-09-10). Falls back to the old substring match when `attached_node` is absent, so an older manifest still works (pure functions, no I/O)
    inspect.py           — behind `ts dbt inspect`: read a compiled manifest and answer Path N vs Path Y (inspect_manifest), plus `group_manifest_models` (the `--model-tables` grouping, emitting `alias or name` — a model with `alias:` materialises under the alias and that is the ONLY name ThoughtSpot matches; emitting `name` 400s the whole generate-tml call, open-items #15) and `ts_join_tests`. The join scan deliberately uses the SAME predicates as manifest.py's reader, so inspect can never recommend Path Y for a join graph build-model then fails to find. Path Y is forced by any of: a ts_join_* graph, model-level ts_rls_rules (the server-side sync does not read the tag), or MetricFlow metrics (pure functions, no I/O)
  dbt_build_export.py  — ThoughtSpot Model TML → dbt project scaffold (build_dbt_export) behind `ts dbt-export build` — ts-convert-to-dbt, Case A (new project) only; Case B (update an existing project in place) is dbt_diff.py + commands/dbt_export.py's `diff`/`sync`. Emits TWO artifacts: `models/schema.yml` (PRIMARY — plain dbt `columns:`/`data_tests:` with ThoughtSpot's `ts_*` metadata tags under `meta:`, the mechanism the base dbt sync already reads once compiled into manifest.json; exhaustive tag list verified against docs.thoughtspot.com's dbt-integration-metadata-tags page, current dbt `config:`/`arguments:` syntax live-verified against `dbt-fusion parse` + a compiled manifest.json inspection 2026-08-27 — the older bare `meta:`/`tests:` shape ThoughtSpot's own docs example shows hard-errors in that build) and `models/semantic_models.yml` (SECONDARY, optional — legacy top-level `semantic_models:`/`metrics:` MetricFlow spec, since ThoughtSpot's separate MetricFlow-import feature is documented only through "dbt 1.7 and earlier," predating dbt's current nested semantic-layer spec; not live-verified against ThoughtSpot's own importer). ThoughtSpot's model_tables[].joins become MetricFlow entity relationships in the secondary artifact AND a `relationships:` data test with `ts_join_*` meta in the primary artifact — the two mechanisms are complementary, not redundant, since only the primary one can express join cardinality/type/name at all. Generates a dbt project only; does not run dbt or upload anything — see agents/cli/ts-convert-to-dbt/references/open-items.md for the connection-type-specific hand-off (ZIP_FILE needs a local compile+zip step; DBT_CLOUD needs a git commit + dbt Cloud job run, no local artifact at all) and the remaining open questions (dbt-core compatibility unverified, formula translation not implemented). Formula columns are reported in skipped_formulas, not silently dropped (pure functions, no I/O)
  spotql_ops.py        — Aggregate-function classification (AGGREGATE_FUNCS/is_aggregate_expr/classify_expr/outermost_func/classify_model_columns; incl. semi-additive last_value/first_value → SUM wrapper) behind `ts agentql classify-columns` (pure functions, no I/O)
  publish_plan.py      -- Orgs Publishing planning engine: field-variance clustering (build_clusters/extract_table_fields/suggest_variable_name) + the value matrix (build_value_matrix/expand_pattern/coverage_report) behind `ts publish export`/`resolve`/`apply`/`rollback` (incl. build_apply_plan/rollback_steps, which record each field's ORIGINAL static value because unparameterize substitutes rather than clears). Clusters by DISTINCT VALUE because a variable holds one value per scope, so N tables sharing a schema need one variable, not N. Also holds `published_org_ids(header)` -- THE one statement of what `metadata_header.orgIds` means (owning Org PLUS every Org published to, so `ownerOrgId` is excluded and the result reads as "additionally visible in"), shared by `ts publish status` and `ts security column-rules` rather than restated in each; restating it is how the two readings diverged, with CSR treating every table on an Orgs-enabled cluster as published (pure functions, no I/O)
  publish_apply.py     — Orgs Publishing apply-plan assembly: multi-root closure merge (merge_closures/publish_targets/publish_type_for_root) + ordered plan and rollback record (build_apply_plan/rollback_steps); split from publish_plan.py under the file-size gate and re-exported from it (pure functions, no I/O)
  share_plan.py        — `ts share` planning engine: grant-manifest parsing (parse_grant_rows), the table/column exclusivity rule (find_exclusivity_conflicts/format_conflicts — sharing a table grants EVERY column, so a table grant and a column grant for one (org, table, group) are REFUSED, never merged; the check ignores share_mode, NO_ACCESS included, because a revoke-then-grant sequence cannot be safely ordered inside one manifest), API-call batching by audience (build_share_steps — one call per (org, metadata_type, principal-set), everything sorted so a --dry-run plan is diffable), and fetch-permissions flattening (permission_rows) behind `ts share resolve`/`apply`/`status` (pure functions, no I/O)
  csr_plan.py          -- `ts security column-rules` planning engine (Column Security Rules, the OTHER column-security mechanism -- not `ts share`'s column-level sharing): manifest/flag parsing (parse_rule_flags/parse_rule_rows, where an empty group list -- "COL=" -- is the sentinel for "secured, nobody"), payload assembly (build_update_payload, where `column_security_rules` is a REQUIRED field so `clear_csr: true` always ships with `column_security_rules: []` beside it, and `group_access` carries an `operation` of ADD/REMOVE/REPLACE with REPLACE the default because it is what makes the call idempotent), step assembly (build_csr_steps, one step per (org, table) because `update` takes a single table per call so its "all or none" rollback is per call and not per run, and pruning is opt-in because the other default would silently unsecure columns absent from an incomplete manifest and leak data), read-back normalisation and diffing (normalise_fetch_response/diff_csr, reading both the documented camelCase `data` envelope and the schema's snake_case bare array since which one a build returns is not knowable from the spec alone), the TML sibling-document route (build_csr_tml/parse_csr_tml_export, exactly the column_alias pattern), and error translation (explain_csr_error, catching the feature-flag 403/10023 case before it reads as a bare permissions problem) behind `ts security column-rules get`/`export`/`resolve`/`apply`/`build`/`import`/`set`/`clear` (pure functions, no I/O)
  tenancy_spec.py      -- `ts tenancy` spec handling: parse/validate/template a topology document (parse_spec, validate_spec, substitute_tenant, unresolved_placeholders). Holds the PER-ORG coherence rules -- a user's group memberships must be in Orgs they belong to, and every group must be declared for THAT Org, because a group name in Primary is a different principal from the same name in a tenant Org and a manifest naming the wrong one fails with `Invalid group identifiers`. Returns ALL problems rather than the first, since topology mistakes are systematic (pure functions, no I/O)
  tenancy_plan.py      -- `ts tenancy` planning engine: ordered idempotent apply steps (build_apply_plan -- Org before its groups before a user joining one, and existing objects skipped so a half-finished run is simply re-run), one-directional drift (diff_topology -- extra cluster objects are NOT reported, or verify would be permanently red on a shared cluster), teardown (build_teardown_plan -- THREE independent gates: the spec's marker, every Org named on the command line, and a user refused if they also belong to an unnamed Org; Primary never deleted), and capture (spec_from_cluster). Re-exports tenancy_spec so callers have one import site (pure functions, no I/O)
  migrate/classify.py -- classify each dependent by WHAT IT SITS ON, which is the number that sizes a tenant's migration -- and it is NOT the object count. Because a View's exposed names survive a repoint, content on a View costs NOTHING (repoint the View and everything above it is done), so 200 Answers over 4 Views is four repoints while 40 Answers straight onto the Model is forty rewrites. kind_of maps subtype -> cost, an unrecognised subtype is UNKNOWN rather than assumed cheap (guessing free would silently drop it from the rewrite set). classify_dependent takes the MOST EXPENSIVE classification for a mixed dependent, since an Answer reading one View and one Model still needs the Model half. build_effort/render_effort_markdown lead with the rewrite count and NAME the Views to repoint, and warn separately about Table-based content -- a Model-level change never reaches it (pure functions, no I/O)
  migrate/rewrite.py -- THE Org-migration transform: rewrite content TML onto a different Model. For each object exactly two things change, the data-source reference (repoint_source -- `fqn` AND `name`/`id`, because resolution falls back to the name when the fqn is dead and a stale name silently binds to the wrong object) and the column names. Uses a DENYLIST not an allowlist: every whole-string match is rewritten except `LABEL_PATHS`, so a reference field the platform adds later is handled for free -- the deliberate trade being that a new LABEL field would be wrongly rewritten, which is the one thing the coverage gate cannot catch. Handles three reference shapes: whole-string, bracketed tokens (substitute_bracketed -- only bracket contents in the map, so `[date].'last 12 months' top 5` and `[formula_X]` survive), and decoration (substitute_decorated -- `Total Segment` -> `Total STRING_1`, longest-match-first so `Order Date` beats `Order`). client_state_v2 is PARSED rather than string-replaced (rewrite_client_state -- only columnProperties[].columnId and systemSeriesColors[].serieName; axisProperties[].id is a stable GUID) because a substring pass over that blob corrupts unrelated chart state. rewrite_view PRESERVES `view_columns[].name` while rewriting `search_output_column`: a View then reads a different Model while exposing the same names, so every Answer and Liveboard built on it needs no migration at all (proven end to end 2026-07-28, including that the untouched content still returns data). residual_references is the completeness gate -- the failure mode of a partial rewrite is an object that imports cleanly and RENDERS WRONG, so "did we catch every field?" has to be an assertion; verified clean against 64 real Liveboards/Answers on se-thoughtspot (pure functions, no I/O)
  migrate/apply_plan.py -- Phase 2 planning engine, now THREE steps (backup, rewrite_views, rewrite_content) where it was eight. The scaffolding steps existed only to avoid rewriting content, and BL-148/BL-149 showed that was never possible. import_mode DERIVES the write mode rather than exposing a flag -- same Org keeps the guid and updates in place, a new Org strips it and creates fresh, and cluster needs no handling because it is a property of the profile. column_map is FLAT across Models because the rewrite is document-wide, which is why find_rename_collisions also refuses one tenant column mapped to different published names in two Models. unfiltered_target_problem refuses to bind tenant content to a published Model with no RLS, and refuses an UNREADABLE check too (pure functions, no I/O)
  migrate/apply_exec.py -- Phase 2 executor: export, rewrite, import. Runs the per-object COVERAGE GATE before writing anything (residual_references), because a partial rewrite imports cleanly and RENDERS WRONG -- so it is caught at plan time rather than by a user later. Views are rewritten before content so that in a new-Org run the View exists before anything references it, and shielded content is never in the content batch at all
  migrate/aliases.py -- per-wave alias assembly (spec step 7). ONE merge per wave, never per tenant: aliases live on the Primary Org's Model with no delta update until 26.10, so every append re-imports the WHOLE document -- per tenant that is O(N^2) across a fleet and past 5 MB each import goes async at 10-15 minutes. translations_from_mapping derives the aliases from the approved `column-mapping.csv` as the exact INVERSE of the rename `apply` performed (`column` = published name, `alias` = tenant's, scope always TS_WILDCARD_ALL), because hand-transcribing them is a step whose mistakes are silent -- a misspelled column aliases nothing and the tenant sees the physical name. missing_org_coverage is THE catastrophic check: the import REPLACES the document, so an export that came back partial silently strips every already-cut-over Org it missed. Coverage is by ORG not by COUNT, since a count is satisfiable by the wrong Orgs -- ten aliases for one tenant pass "ten or more" while nine tenants are wiped -- and naming the Org makes the refusal actionable. The transform and the overlap rule are REUSED from ts_cli/alias.py rather than restated, which is why `flatten_columns` is public there (pure functions, no I/O)
  migrate/discover.py -- what the migration reads before it writes anything, and the ONE place the source/target distinction is decided. OWNERSHIP is the discriminator, never the name: during a migration an Org holds both its own Model and the published master under the SAME name, so `select_source` requires the Org to OWN the Model and `select_target` requires that it does NOT (plus excluding the source GUID outright). A name-only lookup paired a Model with ITSELF in the same-Org topology and reported READY with every column MATCHED and an empty rename map -- a no-op that passed every gate (BL-152). Either selector RAISES `AmbiguousModelName` rather than picking, because both wrong answers are silent: the wrong source migrates the master's own dependents, the wrong target repoints content onto the object it is moving off. `exclude_owner_org_id` must be None across clusters -- Org ids mean nothing between them and `Primary` is `0` on both. Also holds `dependents_through_views` (Views-only, depth-capped, cycle-guarded -- a single-hop walk hides exactly what a View shields) and `subtypes_by_guid` (batched, since what a dependent SITS ON is what sizes the migration). The selection rules are pure (`select_source`/`select_target`) so they are testable without a client; the rest is I/O
  migrate/sets_scan.py -- Phase 0 `ts migrate scan-sets` engine: cohort-column detection (is_cohort_row/extract_cohort_columns -- matched on the COHORT_ PREFIX, because missing a future subtype variant means reporting a BLOCKED Model as clean), the actionable dependent list (normalise_dependents -- Answers/Liveboards only, since "blocked by these four Answers" is a decision a tenant can act on while "blocked" alone is a dead end), and the fleet roll-up (build_scan_report/render_scan_markdown, carrying the DENOMINATOR because "three of twelve" sizes the problem and "three" does not). Detection MUST go through metadata/search: a cohort column is invisible in the Model's TML, so a TML inspection reports a clean Model that is in fact blocked and a lift-and-shift drops the Set silently (pure functions, no I/O)
  promote.py           — Formula promotion merge (extract_answer_formulas/detect_duplicates/map_references/build_merged_model) behind `ts model promote-formula` (pure functions, no I/O; BL-066)
  aggregate/
    __init__.py          — package marker
    signatures.py         — Answer/Liveboard TML -> normalized query signatures (grouping columns, filters, date bucket) behind `ts aggregate signatures` (pure functions, no I/O)
    measures.py           — measure decomposition rewrite plans (SUM/MIN/MAX/COUNT/AVG/ratio classification) for aggregate models (pure functions, no I/O)
    lattice.py            — grain lattice: bucket/coverage rule + candidate generation from signatures + rewrite plans behind `ts aggregate recommend` (pure functions, no I/O)
    scoring.py            — cost-based (profiled) / coverage-based (unprofiled) greedy candidate selection with a marginal-gain curve behind `ts aggregate recommend` (pure functions, no I/O)
    sqlgen.py             — aggregate SELECT / profiling SQL / DDL emission across snowflake/databricks/bigquery dialects behind `ts aggregate profile`/`generate` (pure functions, no I/O); fallback path only as of Task 18 — see spotql_aggregate.py
    spotql_aggregate.py   — Task 18/19: build an AgentQL SELECT for a candidate's grain (build_spotql — measures by display name, raw date columns, no bucket fn; single-component SUM/MIN/MAX/COUNT measures only, AVG/RATIO raise UnsupportedMeasureError) and wrap ThoughtSpot-compiled warehouse SQL as aggregate DDL (wrap_as_ddl — outer DATE_TRUNC+reagg aggregating SELECT when a date descriptor carries a bucket, plain positional pass-through otherwise), reusing sqlgen.build_ddl/_date_trunc for materialization shapes and per-dialect date truncation — the default DDL SELECT source behind `ts aggregate profile`/`generate`, because ThoughtSpot's own SQL generation resolves joins correctly on role-playing/ambiguous-path dimensions where sqlgen.build_select's hand-rolled walker can be wrong (pure functions, no I/O)
    generate.py           — aggregate Table/Model TML assembly + `aggregated_models` association patch on the primary Model, reusing tables.py/model_builder.py rather than hand-assembling TML (pure functions, no I/O)
    rls.py                — RLS extraction + grain-conflict detection + rule propagation onto the aggregate table (extract_rls/rls_filter_columns/candidate_rls_conflict/add_rls_columns_to_candidate/propagate_rls; tuple-keyed, identical-rule dedup) — wired by commands/aggregate.py + aggregate_rls.py (pure functions, no I/O)
    history.py            — match Snowflake QUERY_HISTORY GROUP BY shapes to signatures, producing reweighted signature weights behind `ts aggregate history` (pure functions, no I/O)
  dependency/
    __init__.py          — re-exports mutate.py + backup.py public entry points
    mutate.py             — REMOVE/REPOINT TML dict transforms (apply_remove/apply_repoint dispatchers + remove_columns_from_*/repoint_* helpers) behind `ts dependency mutate` (pure functions, no I/O; BL-083). A View's `view_columns[]` binds on **`search_output_column`**, never `column_id` — that field is absent from real View TML (0 of 265 columns across all 42 Views on se-thoughtspot, 2026-07-30 census), and a formula-backed column binds to `formulas[].NAME`, not `formulas[].id`. Reading `column_id` made the formula path entirely dead, so a removed formula left its surfacing column behind as a dangling reference (BL-191). ## Required dependencies
```

`PyYAML>=6.0` is a required runtime dependency — `tables.py` uses `yaml.dump` to generate
table TML. Do not remove it from `pyproject.toml`.

## connection_name not connection_fqn

The CLI always uses the string display name for connections — never a GUID.
`connection_name` in table specs maps to the `name:` field inside the `connection:` block
in table TML. Passing a GUID where a name is expected will silently produce invalid TML.

## Token cache location

Tokens are cached per-profile in `/tmp/ts_token_<slug>.txt` (permissions 0600) and managed
by `client.py`. Do not change this path without updating the auth documentation in
`agents/cli/ts-profile-thoughtspot/SKILL.md` (Technical Reference section).

## Connection fetch (v2)

`connections get` and `connections add-tables` fetch connection state via the v2
endpoint `POST /api/rest/2.0/connection/search` (helper `_fetch_connection_v2`), adapted
to the legacy `dataWarehouseInfo.databases` shape via `_adapt_v2_databases`. This replaced
the v1 `/tspublic/v1/connection/fetchConnection` endpoint, which was removed on newer
ThoughtSpot Cloud builds (404). The warehouse hierarchy is only populated for
`SERVICE_ACCOUNT` connections; OAuth/PKCE connections return an empty hierarchy (callers
tolerate this — `add-tables` proceeds with new tables only). No remaining v1 endpoints are
used anywhere in the repo.

### Version bump timing

`.claude/rules/versioning.md` governs *when*: bumps happen **at PR time, not
during wip development**. A wip branch may add a dozen commands and still carry
main's version until the PR opens; the bump is then a single step matching the
single merge.

This matters more than diff churn, because the number gets cited. Writing
"added in v0.140.0" into a SKILL.md or coverage matrix while on a wip branch
promises a release that will never exist if the branch merges as one PR — main
jumps straight past it and no user can ever be on that version. If you need to
mark when something arrived mid-branch, say "in this release" and let the PR
assign the number.

Two bumps that *are* correct mid-branch: the branch is genuinely shipping in
stages (each merge is a release), or you are on main for a hotfix.

A defect found and fixed inside the same unmerged branch has **no** "fixed in
vX" — it never shipped. Say so rather than citing a version that implies users
were exposed to it.

## Adding an audit check

3. Add unit tests in `tools/ts-cli/tests/` covering the check's logic.
4. Add a row to `agents/cli/ts-audit/references/check-catalog.md` with the check ID,

6. Run `pytest tools/ts-cli/tests/` and `python tools/validate/check_version_sync.py`.
