Live checks of the TML shapes the recipe generates (`ts recipe period-comparison`).
The generator (`tools/ts-cli/ts_cli/period_comparison/`) takes its Set, formula and
search shapes from these entries, not from the design spec. Its chart section comes from
the user's base Answer; #7 records that it imports and draws.

Status legend: **VERIFIED** (tested live) | **PARTIAL** (part tested live, the rest
named below) | **DEFERRED** (not tested, or out of v1 scope; the reason is stated in the
item)

**Fixture cluster:** profile `simba-test`, the direct-query test cluster (one cluster

UI (#1), though v1 does not use them. **Model:** *1 - Dunder Mifflin Sales (TS Model)* (demo dataset), date

**SpotterCode MCP was not available** in the probing session: the server needs an OAuth

The `answer-level-set-*` fixtures are not v1 shapes; they are kept as evidence for the

## #1 — Answer-level Set on a cluster without the feature — DEFERRED 2026-11-18 (out of v1 scope)

**Out of v1 scope: answer-level Sets dropped (user decision 2026-11-18); carried by BL-601.** The evidence below is kept for that item.

**Docs:** the 26.4.0.cl release notes list "Answer-level Sets Early Access": "To enable
this feature, contact your administrator." The note describes **query** sets only
("generating and consuming Query sets within a single Answer flow"). Neither the release
notes nor `tml-sets` / `column-sets` say whether a **column** set can be answer-level, or
what an import returns when the feature is off.

**Live, feature on:** answer-level column Sets **work** on the direct-query test cluster.
An earlier reading of this item said such a Set "imports and then fails at query time".
That was wrong: the failure came from `ts tml verify-render`, which cannot judge an Answer
with an answer-level Set.

| Step | Result |
|---|---|
| Import an Answer whose `cohorts[]` holds a GROUP_BASED Set and no formula uses it (`answer-level-set-no-formulas.answer.tml`) | **OK**, and the export returns the `cohorts[]` entry intact. (The layout B exports in #8 also add an `owner:` key holding the author's user name.) |
| Put the same Answer in a Liveboard and run `ts tml verify-render` | Fails: `No data source found for the query.` Same with a one-condition `EQ` Set on `Customer State`. The other five tiles on the same board (reusable Set and formula buckets) rendered |
| **Control (user, 2026-11-18):** an Answer built in the UI with an answer-level Set: one `cohorts[]` entry with `owner`, `worksheet: {id, name, fqn}`, `config.null_output_value: Ungrouped values`, `config.combine_non_group_values: true`, GROUP_BASED, one `BEGINS_WITH` condition on a STRING column | **Shows data in the UI.** Embedded in a probe Liveboard, it fails `ts tml verify-render` with the same `No data source found for the query.` |
| Reference the answer-level Set from an Answer formula | **Import fails**, error 14516. A product bug, not a feature switch (see #5) |

So the verify-render failure is an artefact of verify-render, not of answer-level Sets.
**`ts tml verify-render` cannot judge any Answer that carries an answer-level Set.**

**Feature off: not seen.** Only one cluster was available, and it has the feature, so what
an import returns when the feature is off (an error code, or a silent drop) was not seen.
On the one cluster available, import gave no signal about the feature, so a future
answer-level form has no known way to detect "not enabled" and would have to warn the user
up front instead. BL-601 re-opens this when a
cluster without the feature is available.

## #3 — Date-range condition shape and condition count — VERIFIED via docs + live 2026-11-18

**Docs:** `tml-sets` shows only `EQ` conditions with a single dd/mm/yyyy value; it does not
document `filter_value_type`, `date_filter_values`, `EXACT_DATE_RANGE`, `date_period` or
`for_each_period`, and states no limit on conditions or groups.

**Live:** this condition shape imports as a reusable Set, and the export returns it
unchanged (all 70 conditions, the dates in `MM/DD/YYYY`, `date_period` and
`for_each_period` kept):

```yaml
- operator: BW
  column_name: Order Date
  filter_value_type: DATE_FILTER
  date_filter_values:
  - type: EXACT_DATE_RANGE
    oper: between
    date_range:
      start_date: 11/29/2019
      end_date: 12/02/2019
    date_period: DAY
    for_each_period: NUM_DATE_PERIODS
```

AgentQL over the reusable Set (`ts agentql generate-sql`) shows how it compiles: one
`CASE WHEN` in the main query, each condition as
`date_col >= to_date('2019-11-29', 'yyyy-MM-dd') AND date_col <= to_date('2019-12-02', 'yyyy-MM-dd')`
(both bounds inclusive), conditions joined by `OR`, and the groups tested in order (the
event group first, then `ELSE CASE WHEN` for the comparison group, then the
`null_output_value`). For 2019 the Set split the year into 4 event days, 24 comparison
days and 337 others (365), so no day was counted twice.

**Condition count — import has no limit up to 1,400; queries fail well before that:**

| Conditions (event + comparison) | Import | Query (AgentQL over the Set) |
|---|---|---|
| 70 (10 + 60) | OK, round-trips | OK |
| 168 (24 + 144) | OK, round-trips | OK |
| 294 (42 + 252) | OK | OK |
| 406 (58 + 348) | OK | Compiles (`generate-sql`); not executed |
| 525 (75 + 450) | OK | OK |
| 700 (100 + 600) | OK, round-trips | **Fails:** error 10000, `java.lang.StackOverflowError` in `SqlQuerySerializer.serializeFunctionArgument` |
| 1,400 (200 + 1,200) | OK, round-trips (474 KB TML) | Fails: `ReadTimeout`, then a `StackOverflowError` |

The stack trace shows the serializer recursing once per `OR`, so the ceiling is a
recursion depth, not a file size. The data do not say whether it is set by the largest
group or by the total number of conditions: every probe kept the same 1:6 split, so the
query failed between 450 and 600 conditions in the comparison group, which is also between
525 and 700 in total. The recipe's normal case (10 years × 6 prior weeks = 60 in the
comparison group) is far below it, but `--years` over a long span with many prior weeks
can reach it. **The generator refuses, with a clear message, any group above a safe cap**
of 300 conditions per group. The envelope below is what was rendered; the true limit may
differ by build and by JVM stack size.

Large queries also slowed the cluster: while the 1,400-condition compile ran, other
AgentQL calls returned an empty `UNKNOWN` status and one TML import returned HTTP 500.
Both recovered within minutes.

The formula bucket was checked at 168 windows (a 23 KB formula): it imports and renders.
At 525 windows (72 KB) the client's import call timed out, and a search soon after found
nothing, so it was first recorded as "created nothing". That was wrong: the server finished
the import later. A later search on 2026-11-18 found two copies of the probe Liveboard (one
per attempt, created a minute apart), and both were deleted. Their 525-window tile was
never rendered, so the formula form's own ceiling was not found. **A client timeout on
`ts tml import` does not mean nothing was created:** search again after a few minutes
before retrying.

**Verified envelope at the 300 cap (live 2026-11-18).** Black Friday,
1995–2019 (25 years) × 12 prior weeks: 25 event windows and **300 comparison windows**,
generated by `build_plan`. Each form was built as an Answer with the measures from #4 and
the bucket left out of the search (#7), placed on its own probe Liveboard, and checked with
`ts tml verify-render`, which runs the tile's query:

| Form | Size | Import | Export | `verify-render` |
|---|---|---|---|---|
| Reusable Set (binding `{id, name, fqn}`) | 325 conditions (25 + 300), 110 KB TML | Set OK in about 2 s; Answer and Liveboard OK | Set returns 25 + 300 conditions | `ok: true`, 1 tile, about 66 s |
| Answer formula | 325 windows, a 44,608-character bucket formula | Client `ReadTimeout` at 60 s for the Answer and the Liveboard; both were on the server within 2 minutes | Bucket formula returns all 325 windows | `ok: true`, 1 tile, about 63 s |

So both forms render at 300 windows in the comparison group: that is the verified
envelope. The probe was 25 + 300, while the cap allows 300 in each group, so 300 event
windows (300 years) were never rendered; a real plan has far fewer. No headroom above 300
was measured for either form. Above 300 is not probed, on purpose (large probes slowed
this shared cluster). For the formula
form, a 300-window import outlasts the client's 60-second timeout: the skill text must
tell the user to search for the Answer before re-importing, or a retry creates a
duplicate.

**Worksheet binding on a reusable Set.** `{id, name, obj_id}`, `{id, name}` and
`{id, name, fqn}` all import. The export returns `{id, name}` only; this build does not
export `obj_id`. **Emit `worksheet: {id: <Model name>, name: <Model name>, fqn: <Model
GUID>}`** (ruling 2026-11-18, spec "Generated TML"): the generator has the Model's name and
GUID, not its `obj_id`. The fixture `reusable-set.cohort.yaml` and the 300-condition probe
above use this binding.

## #4 — `sum_if` / `unique_count_if` inside `safe_divide` — VERIFIED live 2026-11-18 (compiles via `ts`; Answer SQL by the user's UI check)

**Docs:** `formula-reference` lists `sum_if(condition, measure)`,
`unique_count_if(condition, column)`, `safe_divide` (returns 0 when the divisor is 0) and
`date` ("returns the date portion of a given date"). Nothing restricts the condition
argument.

**Live (compiles and runs):**

```
safe_divide ( sum_if ( [<bucket>] = '<label>' , [Amount] ) , unique_count_if ( [<bucket>] = '<label>' , date ( [Order Date] ) ) )
```

- Imports in an Answer with the bucket as a reusable Set and as an Answer formula, on the
  DATE column `Order Date`.
- **DATE_TIME:** the Model has no DATE_TIME column, so the probe used an Answer formula
  `add_minutes ( [Order Date] , 90 )` as the date and wrapped every reference in
  `date ( … )`, in both the bucket formula and the denominator. It imports and renders.
  The formula's type was not read back, so this proves `date ( )` accepts the expression,
  not that a physical DATE_TIME column behaves the same.
- All five Answers using these measures rendered in a probe Liveboard
  (`ts tml verify-render`: `ok: true`, 5 tiles).

**The Answer's SQL: VERIFIED by the user's UI check, 2026-11-18.** No `ts` command returns a
saved Answer's SQL or rows (BL-600), and `ts agentql` runs against the Model, so it cannot
see Answer formulas. The user opened the query view of both Answers that
`tools/smoke-tests/smoke_ts_recipe_answer_period_comparison.py` created (reusable Set and
formula forms, `--no-cleanup`): no `CROSS JOIN`, and the sums and distinct-day counts come
straight from the fact table. See "End-to-end" below.

**DATE_TIME moved to #9.** The `date ( )` probe above stands; the cases a DATE_TIME column
leaves untested, a reusable Set among them, are tracked there.

## #5 — Bucket compared by name in a measure — VERIFIED via docs + live 2026-11-18 (answer-level Set rejected: SCAL-353379)

**Docs:** no page shows a Set referenced inside a formula.

**Live:**

| Bucket form | Reference in the measure | Result |
|---|---|---|
| Reusable Set | `[<Set name>] = '<label>'` | **Imports and renders** |
| Answer formula | `[formula_<bucket name>] = '<label>'` | **Imports and renders** |
| Answer-level Set (`cohorts[]`) | `[<Set name>] = '<label>'` | **Import fails**, error 14516 |

The 14516 message, for any formula that names the answer-level Set (also a plain
`if ( [Set] = 'x' ) then 1 else 0`):

```
Internal API failed while getting answer. Error: Formula addition failed. Formula: Average Black Friday Sales, Error: Search did not find "ZZ_probe_period_comparison_bucket_inline = 'Black Friday Days' ," in your data or metadata. Expecting one of the valid keywords, such as, "(", "-", "abs" etc..
```

Moving `cohorts:` before `formulas:` in the YAML, or adding the formulas to an Answer that
already holds the Set (update by GUID), gives the same error. Formulas resolve against
the Model's columns and reusable Sets, not against the Answer's own `cohorts[]`.

**Confirmed with a UI-built Set (2026-11-18).** The user copied their own working Answer
(the #1 control: a UI-built answer-level Set with `owner`, `worksheet: {id, name, fqn}`,
`null_output_value: Ungrouped values`, `combine_non_group_values: true`, GROUP_BASED, one
`BEGINS_WITH` STRING condition) and added one formula,
`sum_if ( [<set name>] = 'Group 1' , [Amount] )`. Import failed with the same 14516:
`Formula addition failed ... Search did not find "<set name> = 'Group 1' ," in your data or
metadata`. So the failure is not a defect in the probes' hand-written cohort: it happens
with every field the UI writes. The user then edited that Answer in the UI: the formulas
the editor would save reference the **reusable** Set only, never the answer-level one. The
user agrees answer-level Sets cannot be referenced in formulas and treats it as a
**product bug**, filed as **SCAL-353379**. v1 drops answer-level Sets rather than wait for
a fix; BL-601 cites SCAL-353379.

**Minimal repro, as filed in SCAL-353379** (synthetic; checked live 2026-11-18 on the
direct-query test cluster, with probe names in place of `Repro Set` and the Answer name). Replace `{model_name}` and `{model_guid}` with any Model that
has a STRING column `Customer State` and a measure `Amount`:

```yaml
answer:
  name: Answer-level Set in a formula (repro)
  tables:
  - id: '{model_name}'
    name: '{model_name}'
    fqn: '{model_guid}'
  formulas:
  - id: formula_Group 1 Amount
    name: Group 1 Amount
    expr: sum_if ( [Repro Set] = 'Group 1' , [Amount] )
  search_query: '[Repro Set] [Amount] [formula_Group 1 Amount]'
  answer_columns:
  - name: Repro Set
  - name: Total Amount
  - name: Group 1 Amount
  table:
    table_columns:
    - column_id: Repro Set
      show_headline: false
    - column_id: Total Amount
      show_headline: false
    - column_id: Group 1 Amount
      show_headline: false
    ordered_column_ids:
    - Repro Set
    - Total Amount
    - Group 1 Amount
    client_state: ''
  display_mode: TABLE_MODE
  cohorts:
  - name: Repro Set
    worksheet:
      id: '{model_name}'
      name: '{model_name}'
      fqn: '{model_guid}'
    config:
      cohort_type: SIMPLE
      cohort_grouping_type: GROUP_BASED
      anchor_column_id: Customer State
      groups:
      - name: Group 1
        conditions:
        - operator: EQ
          value:
          - CA
          column_name: Customer State
        combine_type: ANY
      null_output_value: Ungrouped values
      combine_non_group_values: true
```

| Import (`ts tml import --create-new --policy ALL_OR_NONE`) | Result |
|---|---|
| As above | `ERROR`, 14516: `Formula addition failed. Formula: Group 1 Amount, Error: Search did not find "Repro Set = 'Group 1' ," in your data or metadata.` Nothing is created |
| Same file with `formulas: []`, the formula left out of `search_query`, `answer_columns` and `table` | **OK**: the Answer imports, so the Set itself is valid and the formula is the only cause |

Expected: the formula resolves `[Repro Set]` against the Answer's own Set, as it does for a
reusable Set of the same name (see the table above), and as the UI shows the Set as a
column of the Answer.

## #6 — How an Answer references a reusable Set — VERIFIED via docs + live 2026-11-18

**Docs:** `tml-sets`: "If a set is used in an answer then exporting the answer with
associated objects will export the set definition", as a separate file. Nothing about a
GUID reference inside the Answer.

**Live:** **by name only, with no `cohorts[]` entry.** The Set name goes in
`search_query` (when the bucket is searched) and in the formulas. The Answer imports, and
its export has no `cohorts` key. The user's working base Answer, exported from another
cluster, has the same shape.

Adding `cohorts: [{name: <Set name>, guid: <Set GUID>}]` **fails**:

```
Internal API failed while getting answer. Error: Duplicate cohort name: zz_probe_period_comparison_set found in data source: <model guid>
```

The server reads every `cohorts[]` entry as an answer-level Set to create, and the name
clashes with the reusable Set. So `thoughtspot-answer-tml.md` ("the `cohorts[]` entry …
will include a GUID reference") is wrong, and the recipe's second pass needs no Set GUID:
import the Set first, then the Answer, which names it. The Set itself is bound to the
Model with `worksheet: {id: <Model name>, name: <Model name>, fqn: <Model GUID>}` (#3).

## #7 — Bucket placement in `search_query` — VERIFIED live 2026-11-18 (imports and renders via `ts`; one row per year and the chart by the user's UI check)

**Docs:** nothing specific. In search, every attribute in the query is a grouping column.

**Live:**

| Bucket form | (a) bucket in `search_query` | (b) bucket left out |
|---|---|---|
| Reusable Set | Imports, renders | Imports, renders |
| Answer formula | Imports, renders | Imports, renders |

(Answer-level Sets are out of v1 scope. Because no measure can name one, a layout for them
would need the bucket in the search as a grouping column; #8 records that probe for BL-601.)

With (b) the measures still resolve: they reference the bucket themselves, so it does not
have to be searched. When the bucket is in the search, the server's own chart choice on
import is `ADVANCED_LINE_STACKED_COLUMN` with the bucket among `chart_columns`, which
stacks by bucket, so the bucket is being treated as a grouping column. With (b) it picks
`ADVANCED_COLUMN` over year and the three measures.

**Not observable via `ts`:** rows per year. No `ts` command returns a saved Answer's or a
Liveboard tile's rows (`ts tml verify-render` reports only whether tiles render). By search
semantics, (b) leaves `[Order Date].yearly` as the only attribute, which gives one row per
year. **Ship (b).**

**Rows per year: VERIFIED by the user's UI check, 2026-11-18.** On both Answers created by
`tools/smoke-tests/smoke_ts_recipe_answer_period_comparison.py` (reusable Set and formula
forms, `--years 2017-2019`), the user saw exactly three rows: 2017, 2018 and 2019.

**The chart: VERIFIED, 2026-11-18.** The v1 probes (#3 to #7) were TABLE_MODE, and #8's
CHART_MODE probes used a plain COLUMN chart, so the generator's chart (CHART_MODE,
ADVANCED_COLUMN, `custom_chart_config`, `custom_visual_props`, trimmed `client_state_v2`,
from the user's base Answer) was first imported by the smoke test. It imports, and the
export keeps its chart type and display mode (`ADVANCED_COLUMN`, `CHART_MODE`; nothing else
in the chart was compared), `ts tml verify-render` renders both
tiles, and the user saw it draw: year on the x-axis, the three measures on one y-axis, the
template's colours. The TABLE_MODE fallback was not needed.

**Round-trip facts for the verify step (spec step 8) and the smoke test's checks:**

- With (b), the bucket is absent from `search_query`, `answer_columns[]`, the table and
  the chart; the reusable-Set form's export has no `cohorts` key (#6).
- The server reorders `formulas[]` on export and adds `was_auto_generated: false` to each.
  Compare formulas by `id`, not by position.
- `tables[].fqn` is dropped on export unless the Answer is exported with `--fqn`.

## #8 — Hiding the `<other>` bucket in the answer-level layout (layout B) — DEFERRED 2026-11-18 (out of v1 scope); imports and round-trips verified live, rendering never checked

**Out of v1 scope: answer-level Sets dropped (user decision 2026-11-18); carried by BL-601.** The evidence below is kept for that item.

**Docs:** not consulted for this item (the MCP was unavailable; see the header). The
repo's `thoughtspot-sets-tml.md` describes `combine_non_group_values: true` only as
"group remaining rows into 'Other'", and says nothing on filtering an Answer by a Set's own
values.

**The layout** (probed before the v1 decision; fixture
`answer-level-set-layout-b.answer.tml`): `search_query` =
`[Order Date].yearly [<Set>] [formula_Average Daily Sales]` + the date-range filter; chart
`COLUMN` with `x: [Year(Order Date)]`, `y: [Average Daily Sales]`, `color: [<Set>]`; the
answer-level Set has two groups (event 2 windows, comparison 12 windows, from #3) and
`null_output_value: Not Black Friday`. The date-range filter alone still leaves every
non-window day of each year in `<other>`, which would draw a third bar per year.

**The measure as the spec wrote it does not import.** `safe_divide ( sum ( [Amount] ) ,
unique_count ( date ( [Order Date] ) ) )` fails with 14516: `Search did not find
"unique_count ( date (" in your data or metadata`. `unique_count ( [Order Date] )` fails the
same way. The plain distinct-count function is spelled with a **space**,
`unique count` (see `thoughtspot-formula-patterns.md`); only the conditional form is
`unique_count_if`. This imports:

```
Average Daily Sales = safe_divide ( sum ( [Amount] ) , unique count ( date ( [Order Date] ) ) )
```

**Live:** four probe Answers, each the layout above plus one variant. All four import
(`ts tml import --create-new --policy ALL_OR_NONE`), and the export returns them as below.

| Variant | Import | What the export returns |
|---|---|---|
| Control: no Set filter, `combine_non_group_values: true` | OK | Unchanged |
| (a) search filter `[<Set>] != 'Not Black Friday'` | OK | `[<Set>] != 'not black friday'`: the value is lower-cased; the rest unchanged |
| (b) search filter `[<Set>] = 'Black Friday Days' '6 Prior Weeks'` | OK | Rewritten to `[<Set>] = [<Set>].'black friday days' [<Set>].'6 prior weeks'`: each value qualified by the Set name and lower-cased |
| (c) `combine_non_group_values: false`, no Set filter | OK | Unchanged (`combine_non_group_values: false` kept) |

In every export the chart (`COLUMN`, `x` year, `y` measure, `color` Set) round-trips, the
`answer_columns[]` are reordered (measure, year, Set) but complete, and the cohort gains an
`owner:` key. The four Answers share one answer-level Set name and all imported, so an
answer-level Set name only has to be unique against the Model's **reusable** Sets (#6),
not across Answers.

**Rendering: never checked.** `ts tml verify-render` cannot judge an Answer with an
answer-level Set (#1), and no `ts` command returns an Answer's rows. The four probe Answers

## #9 — A DATE_TIME date column — DEFERRED 2026-11-18 (test Model has only DATE columns)

Split out of #4 on 2026-11-18, when #4's SQL check passed. **Why deferred:** the fixture
Model's date columns are all DATE (`Order Date` is DATE in the Model and in the warehouse),
so no live probe could use a real DATE_TIME column. Tracked as **BL-603** (target
2027-02-28), which also carries a fourth case, the `ts_user_timezone` variable. Three
cases are untested:

1. **The formula form on a real DATE_TIME column.** #4's probe used an Answer formula,
   `add_minutes ( [Order Date] , 90 )`, as a stand-in and wrapped every reference in
   `date ( … )`. It imports and renders, but it proves only that `date ( )` accepts that
   expression, not that a physical DATE_TIME column behaves the same.
2. **A reusable Set on DATE_TIME.** A Set condition takes a column, not an expression, so
   `date ( )` cannot be applied; the inclusive end bound of each window may drop that day's
   rows after midnight.
3. **The `search_query` year filter's end bound.** `[<date>] between [<date>].01/01/<first>
   and [<date>].12/31/<last>` names the bare column in both forms, as does the `.yearly`
   grouping. On DATE_TIME, whether `.12/31/<last>` keeps 31 December's rows after midnight
   is untested. It matters for a window ending on 31 December of the last year in the
   windows table (a dropped year moves the filter's end year back). Built-in events reach
   it: `--event christmas --length 7` (25 to 31 December), `--event boxing-day --length 6`
   (26 to 31 December) and `--event christmas --offset 3` (28 to 31 December) each produce
   an event window ending 31 December, and so can a custom event or comparison window. At
   the default six prior weeks each built-in case also needs a clash choice: a comparison
   window holds Black Friday or Cyber Monday, so without `--on-clash` the command exits 2
   and writes nothing. Custom comparison windows are not clash-checked, so they never exit 2.

**How the skill handles it now (spec, "Date column type"):** on a DATE_TIME column it offers
only the formula form, and says why: the bucket formula and the measures wrap the date
column in `date ( … )`, and a Set cannot. It also says the formula form is itself unverified
there (case 1). For case 3, which applies to both forms, it warns when a window ends on
31 December of the last year in the windows table: the agent tells the user and asks them
to check that year's figures, or offers to end the window a day earlier (SKILL.md Steps 5
and 6).

**Exit:** a Model with a real DATE_TIME date column, with data on 31 December late in the
day. Generate both forms on that column, plus a window ending on 31 December of the last
year in the windows table (`--event christmas --length 7 --on-clash skip`), and compare the
rows with an oracle that casts the column to DATE.
