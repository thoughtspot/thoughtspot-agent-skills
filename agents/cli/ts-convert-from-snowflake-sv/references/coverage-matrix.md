# Coverage Matrix: Snowflake Semantic View → ThoughtSpot Model

What the `ts-convert-from-snowflake-sv` skill maps and what it does not.
Use this as the canonical limitations reference.

---

## Mapped Constructs

### Structure and Schema

| # | Semantic View Construct | ThoughtSpot Equivalent | Notes |
|---|---|---|---|
| 1 | `tables (DB.SCHEMA.TABLE)` block | `model_tables[]` entries | |
| 2 | `tables (DB.SCHEMA.VIEW)` — view-backed sources | `model_tables[]` entries | TS tables can point to views |
| 3 | Table aliases (explicit + implicit) | `model_tables[].name` | Correct inbound. **The alias does not survive the return leg unless it disambiguates** — live-measured in the 16-pattern round-trip fidelity study (2026-09-08): role-played aliases over one physical table survived, a single-use alias was replaced by the physical name, so every query citing that alias fails on the regenerated view. | 4 | `primary key (col)` on table entries | Join target identification | Not written to TML (Model TML has no key concept). | 5 | Table-level `comment='...'` | `table.description` | Separate Table TML update (Step 6D, which needs Table TMLs fetched from a live instance). **Unreachable on the documented file-only path**, which emits `{model_name}.model.tml` only — table comments are silently dropped there. See BL-176. |
| 6 | Top-level `comment='...'` (after metrics) | `model.description` | Correct as of ts-cli v0.138.0. **Was dropped on every SV carrying verified queries** — `ai_verified_queries` was treated as one of the blocks the comment follows, so the search window opened after that block's closing paren, past the comment Snowflake requires to come first. ### Joins and Relationships

| # | Semantic View Construct | ThoughtSpot Equivalent | Notes |
|---|---|---|---|
| 7 | `relationships (REL as FROM(FK) references TO(PK))` — equi joins | `joins[]` inline on the FROM table entry | **The named form only.** Snowflake also accepts — and `GET_DDL` preserves — the *unnamed* form `FROM(FK) references TO`, used by 2 of 5 patterns in one group of the 16-pattern round-trip fidelity study (2026-09-08). `_RELATIONSHIP_RE` (`sv_parse.py:100`) requires the `REL as ` prefix, so an unnamed relationship is dropped with `unsupported: []` and exit 0; the resulting joinless Model is rejected (*"Schema validation failed"*). Adding a name by hand is the entire fix. See BL-248. |
| 8 | `references TABLE(between START and END exclusive)` — range joins | `joins[].on` with `>=` / `<` expression | **The bare range only.** The **compound** form `references TO(COL, between S and E)` — equality column *plus* range, which is the form a range join normally needs — silently loses its equality column at `parse-sv`. Measured on 2 of 2 range-carrying patterns in the 16-pattern round-trip fidelity study (2026-09-08): `to_cols` comes back as the two range endpoints, `COL` gone, and **both column lists stay length 2** so nothing downstream detects the misalignment. ThoughtSpot then refuses the import with an invalid join expression. Implementation drift from row 9: the asof branch of `_build_join_on` zips all pairs and handles a leading equality column; the range branch ignores `from_cols[1]`. See BL-249. |
| 9 | `references TABLE(COL1, ASOF COL2)` — ASOF joins | `joins[].on` with `=` on COL1, `>=` on ASOF col | **Accurate as a description of the emitted TML; NOT a statement of coverage — this construct returns materially wrong numbers with no error.** `>=` matches *every prior row* where ASOF matches only the latest. Live-measured in the 16-pattern round-trip fidelity study (2026-09-08): the pattern's own Q1 returns 3,800 inbound against a true 2,100, and the outbound leg drops the ASOF column pair entirely, collapsing to a single-column equi join for 5,100. Both silent, both clean-linting, `A_vs_C` 0/3 on both legs. `>=` cannot express ASOF semantics in a ThoughtSpot join at all. See BL-240 — declining the construct loudly is preferable to today's behaviour. |
| 10 | Composite equi-joins (`FROM(C1,C2) references TO(C1,C2)`) | `joins[].on` with multiple `=` pairs | |
| 11 | Joinless SVs (no `relationships` block) | 4-option join discovery workflow: PK/FK, column overlap, manual, separate models | |
| 40 | Join `type` and `cardinality` — ThoughtSpot join semantics with no `CREATE SEMANTIC VIEW` representation | `joins[].type` / `joins[].cardinality` inbound; **nothing on the return leg** | **Dropped on every outbound leg, silently — 22 relationships across 9 patterns, every one that reached `build-sv`** (19 on a leg that deployed), live-measured in the 16-pattern round-trip fidelity study (2026-09-08): `DROPPED join attrs on <rel>: type=LEFT_OUTER, cardinality=MANY_TO_ONE`. **No rollup or structural comparison sees this**, because relationships are matched on endpoint tuples only, so a re-imported view silently acquires default join semantics — a join-semantics change with a numeric consequence (inner-vs-outer changes row counts) and, until this row, no declaring entry anywhere in the matrix. Same class as the OSSIE review's F1. See BL-263. |

| 23 | Window functions: `OVER (PARTITION BY ... | 24 | `PARTITION BY EXCLUDING` | `group_aggregate(... query_groups()-{dim})` | **Not implemented for a qualified dimension reference** — which is the spelling `GET_DDL` emits. A loud skip, unlike row 25. See BL-260. |
| 25 | Cumulative: `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | `moving_sum(group_aggregate(agg(...), {[T::PK]}, query_filters()), -1, 0, [T::order_col])` | Cannot nest aggregates directly in `moving_sum`; must wrap in `group_aggregate` first. **CONTRADICTED by the 16-pattern round-trip fidelity study (2026-09-08): this form is not what the code emits when a fixed `PARTITION BY` is present.** It emits bare `cumulative_sum ( inner , order_col )` and **drops the partition silently**, turning year-to-date into a lifetime running total with no annotation. `_translate_window` binds `partition` and reads it only on the non-framed `group_*` fall-through; the `cumulative` and `moving` branches never reference it. | 26 | Metric-on-fact resolution (`AVG(table.fact_name)`) | `average([formula_<id>])` | References the fact by formula `id`, derived from the fact's display name by the same function `build-model` mints ids with. A **passthrough** fact (right-hand side is a bare physical column, the shape a Cortex-Analyst model emits) is a `columns[]` entry, not a formula, so a reference to it resolves to `[TABLE::col]` instead — resolution step 1. **This premise did not hold in the round-trip fidelity study: the passthrough fact came back as a `formulas[]` entry, not a `columns[]` entry** (`column_type` now follows the data type — see row 16), so the `[TABLE::col]` path was not the one taken; the consequence of the `formulas[]` route is untested. | 27 | Double aggregation / metric-on-metric (`AVG(table.count_metric)`) | `average(group_count([T::col], [DIM::pk]))` | **CROSS-TABLE only.** `group_*` shorthands, grouping on the PK of the parent (TO) side of the relationship connecting the two metrics' tables; full `group_aggregate(..., {key}, query_filters())` when the inner aggregation has no shorthand or the inner expression is not a simple aggregate. Every double aggregation carries a 🔄 review annotation — the grouping key and relationship direction are not machine-verifiable. Two cases are **skipped and flagged** instead: the inner metric aggregating the grouping column itself (`group_count([X],[X])` = 1 per group), and an SV cycle. Fixed and live-re-verified 2026-07-30 (BL-178). **The metric-on-metric limitation is real but this row described both its trigger and its failure mode wrongly — REFUTED TWICE in the 16-pattern round-trip fidelity study (2026-09-08), on two different shapes (same-table, then cross-fact).** (a) **The discriminator is qualification, not same-table-ness.** On a cross-fact pattern, two metrics referencing a *bare* derived-metric identifier failed while a third survived by inlining — same table relationship, opposite outcomes. (b) **The failure is an upstream `translate-formulas` skip, not the documented loud `I13` exit 1.** `build-model` exited **0**, `import_status: "imported"`, `lint_findings: []`; the constructs were dropped one stage earlier with *"no table for bare identifier 'total_revenue' (default alias '' not found)"* and landed in `skipped[]`. Nothing dangling ever reached TML assembly, so I13 could not fire. Declared, but not loud. The fix is still to inline the inner aggregation — **BL-194**, whose characterisation needs updating with this evidence. |
| 28 | Window metrics referencing other metrics | Combined window + double-agg translation | Shares row #26/#27's resolver. **Now exercised on a live fixture (2026-09-08) and the row's former optimism is not supported: 0 of 3 window-metrics-on-metrics survive** — two skipped at translate (`PARTITION BY EXCLUDING` mis-parsed, BL-260; `LAG` unmapped) and one rejected at Model import. The window **frame** itself does survive: a hand-repaired variant returned all 35 year-to-date rows identical to the original, so the failure is not frame widening. |
| 29 | Duplicate `column_id` detection (I8) | Formula with unique `column_id` | Second metric on same column gets formula |
| 39 | Ratio metrics with a `NULLIF(y, 0)` zero-divisor guard | `safe_divide ( ... )` formula | **Changes semantics silently: `x / NULLIF(y,0)` returns NULL when `y = 0`; `safe_divide` returns 0** (and the reverse leg completes the substitution by emitting Snowflake's `DIV0`). 0 participates in `AVG`/`MIN`/ranking where NULL does not. ### Notes on limitations

**L10** is a converter defect rather than a platform limitation: the target mapping exists,
is bidirectional, and is cited in the very message that declines to apply it. It is recorded
here so the drop is declared while BL-180 is open, and should move to Mapped when it lands.

**L11** is informational — the property is absent from the skill's actual (DDL) input, and
is only relevant if a future path consumes the Cortex-Analyst YAML form directly.

**L13 and L14 are the two most dangerous rows in this table**, and neither is a
platform limitation. Both produce a *success* signal over a total loss: L13 imports a
Model with no measures at exit code 0, L14 reports every construct translated with
nothing skipped. Every other unmapped construct here fails visibly or is cosmetic.
Treat an empty `skipped[]` as evidence of nothing until BL-243 and BL-244 land.

**A companion gate gap worth knowing when reading any "clean" result above:**
`ts snowflake lint-ddl` returned no findings on 8 of 8 generated Semantic View DDL
files in the round-trip fidelity study, 4 of which Snowflake rejects outright — while
`ts snowflake parse-sv`, on the same files, put the offending entries in
`unsupported[]`. The repo's own parser refuses its own emitter's output, and the lint
gate's docstring claims exactly the identifier-validity checks it failed to fire. A
clean `lint-ddl` is not evidence that the DDL deploys. See BL-247.

**L1–L4, L8, L9** are low severity — ThoughtSpot has no direct equivalent or the
equivalent is easily achieved via post-conversion coaching (`/ts-object-model-coach`).
