A *silent* wrong answer is a case the translator marked TRANSLATED, that imported cleanly, and that returned a different value from the oracle — nothing warned the user. A *warned* wrong answer is one the translator marked APPROXIMATED and named a trap for. A known-divergence tag explains only the keys it lists; any other wrong key stays unexplained. The oracle is the warehouse itself: each source formula is run as a Databricks SELECT over the same fixture rows ThoughtSpot queries.

In emitted formulas `[T::col]` is the run's scratch Table, `ZZ_FIDELITY_M2_20261006T232755_B7FDAA_TABLE_DELETE_ME`.

**Five silent wrong answers, four root causes** (all TRANSLATED, imported cleanly, no trap):

| BL | Case | Defect | Wrong keys |
|---|---|---|--:|

| BL-357 | `dbx-arith-005` `COALESCE(N1 / NULLIF(N2, 0), 0)` | the same `safe_divide`, which is **NULL** on a NULL operand; the source is 0 | 2/10 |

- **BL-357 is in both SQL translators.** `sv_sql.py` (Snowflake) has the same two rewrites and emits
  the identical formula (offline translation; M0 had no case for either shape, so it never ran). Both
  mapping docs list the rows as equivalences. The exact form is plain `x / y`: ThoughtSpot already
  compiles `/` to `x / NULLIF(y, 0.0)` (visible in every M2 division's compiled SQL).
- **BL-358 is a platform finding.** Our oracle session on the same warehouse defaults to
  `ansi_mode = true`. ThoughtSpot's query over `DBX_DAMIAN` behaved as non-ANSI three ways: the
  overflow wrapped, `CAST(S2 as int)` returned NULL for `'pie'` (`dbx-arith-014`, ERROR_EQUIV, where
  the source raises `CAST_INVALID_INPUT`), and BL-359's out-of-range cast clamped instead of raising.
  The `m2-nonansi` run (same rows, `ANSI_MODE=false`) matches ThoughtSpot on all six scored cases,
  but only **3 of them discriminate** between the two modes:
  - `dbxn-003`, a malformed cast
  - `dbxn-004`, the overflow
  - `dbxn-007`, `CAST(N1 * 1000000 AS INT)`, which clamps to 2147483647 non-ANSI and raises
    `CAST_OVERFLOW` under ANSI

  The other three (`dbxn-001`, `-005` and `-006`, all divisions) agree in either mode, because
  ThoughtSpot's `/` is NULL-safe. *Why* ThoughtSpot's session is non-ANSI (connection property,
  JDBC default, or a session setting) was not established.
- The BL-358 and BL-359 cases expose each other: in an ANSI session the 32-bit cast would have
  raised, which is loud; non-ANSI turns it into a clamped number.

**Warned, not silent: the three BL-333 cases** (`=`, `contains`, and a conditional count on
`= 'apple'`) are case-insensitive in ThoughtSpot: the compiled SQL wraps the column in `LOWER(…)`.
Each is APPROXIMATED with a trap and is wrong only on the mixed-case key its tag names. This is the
documented, accepted BL-333 divergence. `LIKE` and `INSTR`, also BL-333-shaped, are declined.

**Timestamps (the M0 lesson).** `T1`/`T2` are `TIMESTAMP_NTZ`. `Z1`/`Z2` are Databricks `TIMESTAMP`:
an instant shown in the session zone, so the +05:30 literals load as UTC instants. With the oracle
pinned to `TIMEZONE=UTC`, `hour(Z1)`, `datediff(HOUR, Z1, Z2)` and two-argument `datediff(Z2, Z1)`
MATCH, so **ThoughtSpot's Databricks session evaluates in UTC too**. The evidence is narrow: one
zone, and only UTC on both sides. A Databricks source whose session zone is not UTC would differ on
every hour and day boundary. That is the Snowflake TIMESTAMP_TZ lesson again, in a different shape:
here the zone lives in the session, not in the value.
