# Event-period comparison Answer recipe — design

**Status:** built, 2026-11-18 (see "As built" below) · **Date:** 2026-11-18
**Skill:** `ts-recipe-answer-period-comparison` · **CLI:** `ts recipe period-comparison` (new)

## As built (2026-11-18)

The design below is kept as written. Where the build differs, this note wins:

- **Module path.** The generator is `tools/ts-cli/ts_cli/period_comparison/` (`events.py`,
  `windows.py`, `emit.py`, and `templates/answer.yaml`), not `ts_cli/recipes/`.
- **Options.** `--model-name` and `--model-guid` replace `--model` (the command is offline,
  so it cannot look a Model up). Added: `--event-name` (the display name, required for a
  custom event), `--set-name` (the bucket's name in either form), `--on-clash`,
  `--answer-guid`, `--set-guid` and `--data-through` (the last day the data is loaded
  through; a year with a window ending after it is dropped). The ts-cli README lists every
  option.
- **Labels.** The comparison label is singular for one window: `1 Prior Week`.
- **Open item 9.** A DATE_TIME date column is deferred as open item 9 (the test Model has
  only DATE columns), tracked as BL-603. Open items 3–7 are verified; 1, 2 and 8 moved to
  BL-601 with answer-level Sets.

## Intent and why

Retail analysts want one Answer that says "how much did this event lift daily sales over a
normal week?" for every year at once. The worked case is Black Friday weekend (Fri–Mon)
against the six Fri–Mon windows before it, one row per year: average daily sales in the
event window, average daily sales in the comparison windows, and the variance.

Building it by hand took a column Set with ~70 hand-typed date ranges and three formulas.
The hand-built Set drifted: five prior weekends instead of six, no ranges for 2028–2030,
`date_period` missing on the 2027 entries. An earlier version also used a measure computed
at a fixed level, which cross-joined a grand total onto every product and inflated the
numbers. The recipe exists to make that Answer correct by construction, for any event, in
one command.

## Goals

- Generate the Answer for **built-in retail events** — Black Friday, Cyber Monday,
  Christmas Day, Boxing Day, Easter — with dates computed per year, plus **custom events**
  supplied as one start date per year or explicit ranges.
- The user shapes the **event window**: offset from the anchor day and length in days
  ("Fri–Mon" = offset 0, length 4; "just the Friday" = offset 0, length 1).
- Two **comparison modes**:
  1. **Prior N weeks** (default) — N windows of the event's shape, each stepped back by
     whole weeks, same year as the event.
  2. **Custom ranges** — the user lists the comparison ranges per year.
- Two **bucket outputs**, chosen by the user (answer-level Sets are dropped from v1 — see
  Non-goals):
  1. **Reusable Set** (standalone `cohort:` TML, imported first, then referenced).
  2. **Answer formula** (nested `if … then` bucket formula in `answer.formulas[]`). Scoped
     to this Answer only. **Model-level formulas are out of scope**:
     the recipe never edits the Model.
- Measures computed row-level: `sum_if` / `unique_count_if`, wrapped in `safe_divide`.

## Non-goals (v1)

- **Answer-level Sets** (user decision 2026-11-18). Answer formulas cannot name an
  answer-level Set (SCAL-353379), so that form could only offer a reduced layout with no
  variance column, and `ts tml verify-render` cannot check it. Deferred to a dated backlog
  item that cites SCAL-353379 and the evidence in `references/open-items.md` (#1, #2, #5, #8).

- A "same event, last year" (YoY) variance column. The yearly rows already show it side
  by side; a dedicated column needs a cross-year formula shape not yet verified.
- "Same calendar dates last year" comparison — compares unlike weekdays.
- Liveboards, Model edits, or warehouse objects. The recipe produces one Answer (plus one
  reusable Set when chosen) and changes nothing else.

## Anti-goals

- **Silently wrong numbers.** Any construct that can fan out or re-aggregate at another
  level (`group_aggregate`, fixed-level measures) is never emitted. The variance must be
  computed from row-level conditional aggregates only.
- **Overlap between windows.** A day must never be counted in both the event and a
  comparison window, nor in two comparison windows.
- **Hand-written date lists in the skill.** Dates are generated by code, never typed by the
  agent.

## Constraints

- Repo rules: skills call `ts`, never `requests` or inline scripts
  (`.claude/rules/ts-cli.md`); mechanical transformations belong in the CLI (audit angle 11).
- Naming: family 7, `ts-recipe-{artifact}-{concept}` with no platform suffix (pure
  ThoughtSpot) → `ts-recipe-answer-period-comparison`, category `Recipes`.
- **No more than 300 windows per group, both forms.** Both forms rendered live at 25 + 300
  windows; larger probes failed between 525 and 700 conditions, and the data cannot tell a
  per-group limit from a total one (open item 3). The generator refuses past 300 in a group.
- TML invariants: formula cross-refs by id (`[formula_<Name>]`); reusable Set must exist before the Answer that references it is imported.
- Data range: the Answer filters `[date] between` the first and last generated year, so
  years with no data never render.

## Approaches considered

| | Approach | Trade-off | Verdict |
|---|---|---|---|
| **A** | New `ts recipe period-comparison` command generates dates and TML deterministically; thin skill drives the conversation, import and verification | More to build (command, tests, version bump); date maths and 100+ near-identical conditions are unit-testable and cannot drift | **Chosen** |
| B | Skill-only: agent computes dates and writes TML each run | Fast to ship; reproduces exactly the drift seen in the hand-built Set; violates the no-inline-script rule | Rejected |
| C | Answer-formula bucket | Needs no Set feature; scoped to the one Answer (a Model formula would be reusable but means editing the Model, which is out of scope) | **Folded into A** as the second output form |

## Design

### CLI: `ts recipe period-comparison`

New `recipe` Typer group (`tools/ts-cli/ts_cli/commands/recipe.py`), registered in
`cli.py`. Pure generation lives in `ts_cli/recipes/period_comparison.py` so it can be
tested without a cluster.

```
ts recipe period-comparison
  --model <guid|name>            # Model the Answer searches
  --date-column "<col>"          # e.g. "order date"
  --measure-column "<col>"       # e.g. "Amount"
  --event black-friday|cyber-monday|christmas|boxing-day|easter|custom
  --event-dates <file>           # custom only: YAML/JSON, one start date per year, or ranges
  --offset <int>  --length <int> # window shape relative to the anchor day (default 0 / 4)
  --years 2020-2030              # or --last N (counted back from the current year)
  --comparison prior-weeks|custom
  --prior-weeks <N>              # default 6
  --comparison-dates <file>      # custom comparison only
  --bucket reusable-set|formula
  --name "<Answer name>"
  --labels event="…",comparison="…",other="…"   # defaults below
  -o <dir>                       # writes TML; does not import
```

Output (JSON to stdout, per `ts-cli.md` conventions): the generated windows per year, the
comparison step used, any years dropped as unfinished, and the paths of the TML files written. Import is a separate,
existing step (`ts tml import`), so the skill can show the dates before anything lands.

**Event anchors** (one function each, unit-tested against known years):

| Event | Anchor day |
|---|---|
| `black-friday` | day after the 4th Thursday of November |
| `cyber-monday` | Black Friday + 3 |
| `christmas` | 25 December |
| `boxing-day` | 26 December |
| `easter` | Easter Sunday (anonymous Gregorian computus); "Good Friday–Easter Monday" = offset −2, length 4 |
| `custom` | from `--event-dates` |

**Comparison windows (prior-weeks mode):** window *k* (1..N) = event window shifted back
by `k × step` days, where `step = 7 × ceil(length / 7)`. For length ≤ 7 that is one week,
preserving weekdays; longer windows step by whole weeks large enough never to overlap. The
command reports the step it used. For fixed-date events (Christmas) the weekday alignment
is to the event's weekday that year — stated in the output, not hidden.

**Validation (hard errors):** any overlap between event and comparison windows, or between
comparison windows, in custom mode; a custom file missing a year inside `--years`;
`--length < 1`.

**Default labels:** event = `<Event name> Days` (e.g. "Black Friday Weekend Days" when the
user names it so), comparison = `<N> Prior Weeks` or `Comparison Periods`, other =
`Not <Event name>`. Labels are emitted verbatim into the Set groups / formula branches and
into the measure conditions, so they always match.

### Generated TML

**Bucket — reusable Set:** `cohort_type: SIMPLE`, `cohort_grouping_type: GROUP_BASED`,
`anchor_column_id: <date column>`, `null_output_value: <other label>`,
`combine_non_group_values: true`; two groups (event, comparison), each `combine_type: ANY`
with one `BW` / `DATE_FILTER` / `EXACT_DATE_RANGE` condition per window, every condition
carrying `date_period: DAY` and `for_each_period: NUM_DATE_PERIODS`. It has the
top-level `cohort:` key and the `worksheet:` binding `{id: <Model name>, name: <Model name>,
fqn: <Model GUID>}`. No more than 300 conditions per group (open item 3 records how far
each form was rendered).

**Bucket — formula:** single-line nested `if ( (…) or (…) ) then '<event>' else if (…)
then '<comparison>' else '<other>'`, each window as
`( date ( [<date>] ) >= to_date ( 'YYYY-MM-DD' , '%Y-%m-%d' ) and date ( [<date>] ) <= to_date ( … ) )`.

**Measures (reusable Set and formula forms):**

```
Average <Event> Sales      = safe_divide ( sum_if ( [<bucket>] = '<event>' , [<measure>] ) ,
                                           unique_count_if ( [<bucket>] = '<event>' , date ( [<date>] ) ) )
Average Comparison Sales   = same with '<comparison>'
Variance to Baseline       = [formula_Average <Event> Sales] - [formula_Average Comparison Sales]
```

`<bucket>` is the Set name, or `formula_<bucket name>` for the formula form.

**Answer (reusable Set and formula forms):** `search_query` = `[<date>].yearly` + the three measures (the bucket is left out — open item 7) +
`[<date>] between [<date>].MM/DD/<first> and [<date>].MM/DD/<last>`; table and chart
sections follow the base Answer from the user (ADVANCED_COLUMN, year on x, three measures on
a merged y-axis, measure names as colour). The base Answer is kept as a template file in
`ts_cli/recipes/templates/` with placeholders, not regenerated from prose.

### Skill: `ts-recipe-answer-period-comparison`

Steps (independent questions batched, dependent ones one at a time):

1. **Profile** — pick a ThoughtSpot profile (`/ts-profile-thoughtspot` if none).
2. **Model and columns** — find the Model (`ts metadata search`; Models are subtype
   `WORKSHEET`), export its TML, and propose the date and sales columns; user confirms.
   Warn if the sales column is a formula containing `group_aggregate` or another
   fixed-level function (the inflation trap in "Intent").
3. **Event** — built-in or custom; window shape; years.
4. **Comparison** — prior N weeks (default 6) or custom ranges.
5. **Bucket form** — reusable Set or Answer formula. Explain: the reusable Set is shared on
   the Model; the Answer formula is private to the Answer. Model formulas are not offered.
   If the user asks for an answer-level Set, explain it is not in v1 (SCAL-353379: formulas
   cannot name one, so there would be no variance column). If the date column is
   DATE_TIME, offer only the formula form (see "Date column type").
6. **Generate** — run `ts recipe period-comparison … -o <dir>`. If it reports comparison
   windows that clash with other retail events, explain them, offer skip-and-extend
   (recommended), keep, or custom ranges, and re-run with `--on-clash`. Show the final
   windows table for the user to check before import.
7. **Import** — reusable Set first (when chosen), then the Answer, via `ts tml import`.
8. **Verify** — export the Answer back and confirm the bucket, formulas and search round-trip.
   No `ts` command fetches a saved Answer's SQL today (`ts agentql` runs against a Model and
   cannot see Answer formulas), so v1 tells the user how to check the
   SQL in the UI (no `CROSS JOIN`; `sum(... <measure column> ...)` straight from the fact
   table). *Author's call:* adding an Answer-SQL command is out of v1 scope and becomes a
   dated backlog item, so v1 doesn't take on a second new command.

## Decisions from the builder review (author's calls unless marked)

- **Template provenance.** The base Answer and Set came from a Dunder Mifflin demo Model,
  not a customer tenant. The committed template is rebuilt from that export with the
  `guid`, `obj_id`, `owner` and Model binding replaced by placeholders, so no personal or
  instance identifiers are committed.
- **Date column type.** The bucket formula's comparisons and the `unique_count_if`
  denominator are wrapped in `date ( … )`, so on a DATE_TIME column they should count days;
  the Set conditions, the `.yearly` grouping and the Answer's year filter name the bare
  column. Neither form is verified on a real DATE_TIME column (open item 9): the test Model
  has DATE columns only. **Ruling (2026-11-18):** the skill offers only the formula form
  when the date column is DATE_TIME, because a Set cannot wrap the column, and it warns
  when a window ends on 31 December of the last year in the windows table, since the year
  filter's end bound may drop that day's late rows (SKILL.md Steps 5 and 6).
- **Denominator meaning.** The average is per day *with data* in the window
  (`unique_count_if`), as in the base Answer. This is documented in the skill output,
  because it changes when the Answer is filtered (e.g. to one product).
- **Year attribution.** Rows group by the date column's calendar year. Any window that
  crosses 1 January is a **hard error** naming the window, so nothing silently lands in the
  wrong row. If the date column carries a custom or fiscal calendar, the skill warns that
  `.yearly` follows that calendar, not the Gregorian years the generator uses.
- **Partial current year.** The generator drops any year whose event window has not ended
  by the run date (reported in the output). `safe_divide` stays, per the user's standing
  preference, and can no longer produce a "0 then minus baseline" row for an unfinished year.
- **Re-runs.** In scope: the command takes optional `--answer-guid` / `--set-guid`, which
  are written at the TML root so a re-import updates the objects in place. The skill
  searches for an existing Answer or Set with the same name and offers to update it.
- **Reusable Set reference.** Settled by open item 6: the Answer names the Set only, with
  no `cohorts[]` entry, so one command run writes both files. Import the Set first, then
  the Answer. `--set-guid` is only for updating an existing Set in place.
- **Comparison windows that land on another retail event (user's decision).** In
  prior-weeks mode the generator checks every comparison window against the other
  built-in events for that year (e.g. Boxing Day 2025's 4th prior window is Black Friday
  to Cyber Monday). The command never resolves a clash silently: it takes
  `--on-clash skip|keep`, and without the flag it lists the clashes and writes no TML.
  The skill then **explains** each clash in plain words: which window, which event, and
  that keeping it pushes the baseline up and shrinks the measured lift. It **offers**:
  1. **Skip and extend (recommended):** drop each clashing window and take the next
     week further back, so there are still N windows. The output names the substitutes.
  2. **Keep:** use the windows as they are, with the effect stated.
  3. **Custom:** switch to custom comparison ranges for full control.

  The skill re-runs the command with the user's choice. Substitute windows obey the same
  rules: no overlap, no crossing 1 January.
- **"Overlap adjustments" wording.** Removed. Prior-week windows cannot overlap by
  construction; the output reports the step used. Overlap checks apply to custom mode.

## Amendments after live verification (2026-11-18)

Open items 3–7 were verified live on the direct-query test cluster (1, 2, 8 and 9 are deferred); the user confirmed the
answer-level finding with their own Answers.

- **Answer formulas cannot reference an answer-level Set.** Any formula naming it fails
  import with error 14516 ("Search did not find …"), including a copy of a working
  user-built Set with every field the UI writes. Formulas can reference a reusable Set. The
  user regards this as a product bug, filed as SCAL-353379.
- **Answer-level Sets dropped from v1** (user decision, same day). A layout with the Set as
  a grouping column and one measure (`unique count`, with a space) was probed (open item 8)
  and is recorded for the backlog item, not built.
- **Reusable Set and formula forms:** the bucket is left out of `search_query` (open item
  7); the measures name it themselves.
- **`ts tml verify-render` cannot judge an Answer with an answer-level Set**: the user's
  working Answer failed it too ("No data source found"). Recorded for the backlog item.

## Open items (verify live before shipping — `references/open-items.md`)

Items 1, 2 and 8 concern answer-level Sets and move to the backlog item with them.

1. **Answer-level Set availability.** How a cluster without the feature responds to an
   Answer TML carrying `cohorts[]` with no GUID: import error code/message, or silent
   drop. Determines step 7's detection. MCP first (`get-developer-docs-reference`), then a
   live import on one cluster with and one without.
2. **Answer-level Set binding.** The repo schema shows a `worksheet:` block on an inline
   cohort with `fqn:`; confirm whether it is required and whether the Set name must match an
   `answer_columns[]` entry.
3. **Date-range condition shape.** Confirm `EXACT_DATE_RANGE` with `MM/DD/YYYY` dates is
   the import shape (it is the export shape in the user's Set; the repo only records a single-date `EXACT_DATE` shape, and
   `ts_cli/tableau/sets.py` writes a different list form, so neither is reused unverified),
   and that a Set with ~70
   conditions imports. Check whether there is a condition-count limit.
4. **`sum_if` / `unique_count_if` inside `safe_divide`** — confirm it compiles and that the
   SQL stays a single flat query (no CTE fan-out).
5. **Bucket compared by name in measures** — `[<Set name>] = '<label>'` inside an Answer
   formula worked in the base Answer; confirm the same for a reusable Set and for the
   formula form (`[formula_<bucket>]`).
6. **How an Answer references a reusable Set.** `thoughtspot-answer-tml.md` says the
   Answer's `cohorts[]` entry carries the Set GUID; the verified examples reference the
   Set by name only. Settle it live; it decides whether the second pass needs the GUID.
7. **Bucket in `search_query`.** A Set in the search normally groups. With the bucket as a
   grouping column you get up to three rows per year and a meaningless variance. The SQL
   from the user's working Answer grouped by year only, so test both: bucket in
   `search_query` but off every chart axis, and bucket omitted entirely, with the measures
   still resolving. Ship whichever gives one row per year. Applies to both forms.
8. **Hiding the `<other>` bucket in the answer-level layout.** Find the shape that leaves
   only the event and comparison bars: a search filter on the Set
   (`[<Set>] != '<other>'` or `[<Set>] = '<event>' '<comparison>'`), or
   `combine_non_group_values: false`. Verify live; the date-range filter alone still leaves
   every non-window day in `<other>`.
